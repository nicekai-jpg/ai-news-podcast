# 知识图谱抽取（零 LLM 调用）· V1 现状（已归档）

> **归档（2026-11-16）**：本文是 V1 抽取器的现状说明，代码仍在（`business/kg/`、Stage 2.5）。
> V2 完整方案见 [docs/kg_extraction.md](../kg_extraction.md)。

把一篇文章抽成「对象-关系-对象」三元组，**不调用大模型**。

```
文章正文
   │
   ▼
① 词典匹配     实体 / 动作 / 产品（config/nlp）
② 未登录实体   jieba 词性 + 机构后缀 + 英文大写串
   │
   ▼
③ 候选三元组   动作锚点：动作前最近的主体 + 动作后最近的对象
   │
   ▼
④ 依存确认     spaCy 判断主语/宾语角色（可选）
   │
   ▼
⑤ 关系归一     48 个细动作 → 21 个规范关系
   │
   ▼
kg.json（nodes + edges + stats）
```

## 为什么不用 LLM

同一批 10 篇文章的实测：

| 方案 | 三元组 | 成本 | 备注 |
|---|---|---|---|
| LLM 抽取 | 656 条 | 约 10 万 output token | 关系发散，408 种说法 |
| 本方案 | 65 条 | 0 token | 关系收敛，可审计 |

LLM 召回高，但每条都要钱；本方案免费、可复现，召回靠词表和规则补。

## ① 词典匹配

三张表都在 `config/nlp/`：

| 表 | 数量 | 用途 |
|---|---|---|
| `entities.yaml` | 196 | 公司 / 实验室 / 人物 |
| `actions.yaml` | 48 | 发布、融资、收购、裁员… |
| `objects.yaml` | 53 | 模型、产品、芯片 |

匹配规则：英文按单词边界，中文按首字索引、长词优先。

## ② 未登录实体

词表追不上新公司，这一步兜底：

```
jieba 词性 nr（人名）            → 保留
词尾是 公司/集团/实验室/大学     → 保留
出现在标题里的英文大写串         → 保留
其余                             → 丢弃
```

同时挡掉两类误判：

```
泛词      人工智能 / 大模型 / 智能化 / 市场
媒体      量子位 / 公众号 / 作者
```

## ③ 候选三元组

```
句子：阿里巴巴 发布 了 通义千问
        │        │        │
       主体     动作      对象
        └────────┴────────┘
              (阿里巴巴, 发布, 通义千问)
```

规则只有三条：

1. 主体必须是公司 / 机构 / 人物（产品、泛词不能当主语）；
2. 主体在动作前 40 字内，取最近的一个；
3. 对象优先取词表里的模型/产品，没有就截动作后的一段名词短语。

## ④ 依存确认（可选）

装了 spaCy 中文模型时，用依存树核对角色：

| 情况 | 置信度 |
|---|---|
| 主语、宾语都对上 | 0.9 |
| 只对一个 | 0.65 |
| 都没对上 | 0.4 |

没装 spaCy 也不影响主流程，所有候选统一 0.55。

## 已知限制

1. **词表决定召回上限**：主语不在 196 个实体里，基本抽不到；
2. **关系配对靠距离**：动作前后的最近实体不一定是主谓宾，所以低置信边多；
3. **中文分词会拆词**：`方程豹钛9` 这类新词会被切碎，靠未登录实体规则兜底。

## 已接进 v3 流水线（Stage 2.5）

```
Stage 1 采集
   ▼
Stage 2 事件聚类（events + items 在内存里）
   ▼
Stage 2.5 知识图谱          ← 新增，可失败
   │  build_kg() 逐事件抽图
   ▼
data/kg/{date}/kg.json
   ▼
Stage 3 推荐（照常，不依赖图谱）
```

配置在 `config/pipeline_v3.yaml`：

```yaml
stage2_5:
  enabled: true
  min_confidence: 0.4   # 低于该值的边不写盘
  max_chars: 6000       # 每个事件最多拼多少字全文
```

三个约定：

1. **可失败**：抽图抛异常只记 warning，Stage 3 照常跑；
2. **不加重依赖**：spaCy 没装就降级模板（置信度 0.55），不影响出图；
3. **不读已有产物**：直接用 Stage 2 内存里的 `events` + `items`，少一次 IO。

产物：

## V2 事实层方案（2026-11-16，待确认）

> 状态：方案稿，未实施。确认后按此改造；实施完成把这一节改成「现状」。
>
> 目标一句话：**每天产出一批「少而准、每条能回溯原句」的事实卡，覆盖缺口看得见。**

### 一、结论：可行，但原设想要改三点

合理的部分：新闻事实大多是「谁 · 做了什么 · 对象是谁/什么/多少钱」，这类信息靠词表 + 句法能抽，不必用 LLM；零 LLM 还换来可审计、可复现、零成本。

要改的三点：

| 原设想 | 改成 | 原因 |
|---|---|---|
| 先抽自由三元组 | 按 21 类事件模板填槽 | 三元组太自由，关系发散、关键信息缺槽位 |
| 用实体距离判主宾 | 用句法角色判主宾 | V1 错配的主因就是「取动作前后最近的实体」 |
| 一次把覆盖做全 | 缺口报告 + 按月补词表 | 召回上限由词表决定，只能持续补 |

可行性依据（都能在仓库复现）：

| 证据 | 数值 | 出处 |
|---|---|---|
| V1 三元组（10 篇量子位） | 65 条 | `data/kg_audit/kg_batch.json` |
| 我逐条核对的可用边 | 12 条 | 人工核对 |
| 可用率 | 18% | 12 ÷ 65 |
| 置信 0.9 的边 | 4 条 | 4 条全对 |
| 拆子句后能解析出干净主谓宾 | 39 / 65 | 对 65 条边的原句跑 spaCy |
| 实体词表 | 196 个 | `config/nlp/entities.yaml` |
| 动作词表 | 48 条 | `config/nlp/actions.yaml` |
| 对象词表 | 53 个 | `config/nlp/objects.yaml` |

两条推论：

1. **置信分有信号**：0.9 档 4 条全对，说明「句法确认」方向对，值得加强；
2. **解析能力够用**：39 条句子拆开子句后能拿到干净的 主-谓-宾，说明不是中文抽不出，是 V1 没按句法抽。

两条必须接受的限制：

1. 零 LLM 的召回有天花板：词表外的新公司、长尾小事件、结构复杂的长句，抽不到；
2. 只做模板化事件：21 类之外不进事实层，宁缺勿滥。

### 二、V1 错在哪（诊断）

```
原文：联想集团和河北张家口市政府签署合作协议，将推进首座混合词元工厂在张家口落地
V1  ：张家口 --建设--> 算力设备回收与再利用产线
问题：主体错。联想做的事记到张家口头上。
应有：联想 --合作--> 张家口市政府
```

```
原文：2026年，百度成立个人超级智能事业群组，由王颖女士挂帅
V1  ：百度 --成立--> 王颖
问题：对象错。把「挂帅的人」当成了「成立的对象」。
应有：百度 --成立--> 个人超级智能事业群组
```

按影响排序的四个原因：

| 原因 | 现象 | V2 对策 |
|---|---|---|
| 主宾按距离配 | 一个句子里多个实体时主体换人 | 改用句法角色 |
| 不切子句 | 跨句配对，宾语取到别的子句里 | 先分句再解析 |
| 词表只有 196 个实体 | 词表外公司抽不到，覆盖不足 | 未登录实体只进 B 档 |
| 正文噪声区也抽 | 嘉宾名单、报名方式、参考链接变成事实 | 只抽标题 + 导语区 |

```
   ▼
⑤ 判档 A/B/C，标否定与传闻
   │

⑥ 同日多源归并：同一事实多篇报道合成一条，记 sources
   │

```

### 四、关键设计

#### 1 先认「新闻主体」，再抽事实

- **文章主体**：标题里权重最高的受控实体（`entities.yaml` 的 `weight`），作为文章的主事实卡主体；
- **事件主体**：每个子句的句法主语；
- 事件主语不是文章主体时，标 `secondary`（例：文章写联想，张家口政府说政策 → secondary）。

这样「新闻主体是谁」有明确答案，不是一篇拼一大堆三元组。

#### 2 分句 + 依存是主判据

- 按 `。！？；，` 切子句，引号内不切；
- 每个子句用 spaCy 依存树找 root 动词，取 `nsubj` / `dobj`；
- 缺主语或缺宾语 → 这条不成立，进 C 档；
- 解析前用词表做最长匹配，把被切碎的实体拼回去（`英伟达` → `英伟` + `达`）。

拆子句前后对比（同一句）：

```
整句：英伟达任命Harvey C. Jones为公司历史上首位董事会主席
整句解析：英伟 + 达 被当两个词，主宾找错

拆子句后：英伟达 / 任命 / Harvey C. Jones
结果：英伟达 --人事--> Harvey C. Jones ✓
```

#### 3 事件 schema（21 类，每类固定槽位）

| 关系 | 主体槽 | 对象槽 | 可选槽 |
|---|---|---|---|
| 发布 | 公司 | 产品/模型 | 时间 |
| 开源 | 公司 | 模型/权重 | 许可 |
| 更新 | 公司 | 产品/模型 | 版本 |
| 价格 | 公司 | 服务/接口 | 价格 |
| 量产交付 | 公司 | 产品/芯片 | 数量 |
| 部署接入 | 公司 | 产品/服务 | 客户 |
| 支持 | 公司 | 模型/接口 | 范围 |
| 融资上市 | 公司 | 金额/轮次 | 投资方 |
| 收购 | 收购方 | 被收购方 | 金额 |
| 合作 | 公司 | 公司/政府 | 项目 |
| 评测对比 | 公司 | 对手/基准 | 分数 |
| 人事 | 人物 | 职务 | 公司 |
| 裁员 | 公司 | 人数/比例 | 部门 |
| 监管 | 监管机构 | 公司/产品 | 措施 |
| 诉讼 | 原告 | 被告 | 案由 |
| 事故风险 | 公司/产品 | 事件/影响 | 地点 |
| 研究 | 机构 | 成果/论文 | 数据 |
| 活动 | 主办方 | 活动 | 地点 |
| 信息披露 | 公司/人物 | 披露对象 | 时间 |
| 获奖认证 | 公司/产品 | 奖项/认证 | 时间 |
| 其他 | 不填 | 不填 | 不进 A 档 |

#### 4 判档 A/B/C（准确优先的落地规则）

A 档，四条同时满足才进：

1. 主体是受控实体；
2. 句法确认了主宾；
3. 对象类型匹配槽位；
4. 无否定、无传闻。

B 档，能回溯原句、但满足任一条：

1. 主语词表外；
2. 宾语是截断的名词短语；
3. 有传闻或预测标记。

C 档，任一条就直接丢：

1. 无主谓宾结构；
2. 主语是泛词或媒体名；
3. 对象是碎片或代词。

硬门槛：A/B 都必须带原句证据（句子 + item_id + url），没有就丢。

#### 5 否定、传闻、预测单独标，不硬猜

| 标记 | 例子 | 处理 |
|---|---|---|
| 否定 | 没有提供 / 否认 / 不再 | `negated=true`，降 B |
| 传闻 | 消息称 / 据传 / 或将 | `modality=rumor`，降 B |
| 预测 | 预计 / 有望 / 将会 | `modality=forecast`，降 B |
| 已发生 | 宣布 / 签署 / 发布 | `modality=actual` |

「DeepSeek 没有提供语音 API」这种句子，V1 会抽成「DeepSeek 提供语音 API」，差一个否定就是假事实。

#### 6 同日归并、跨日累计

- 同一天多篇报道同一件事：按 `主体 + 关系 + 对象 + 日期` 合成一条，`sources` 记全；
- 跨天不合并：每天留一个时间线点（同一主体昨天发布、今天涨价，两天两条）。

### 六、覆盖度怎么量（回答「数据不足」）

三层覆盖，缺一层都不叫全：

```
① 源覆盖    事实来自哪些源        → 只有 3 个源出事实 = 源没覆盖到
② 事件类型  21 类里这周空几类      → 比如「收购」整周 0 条 = 漏
③ 实体域    公司/人物/机构/产品    → 只看得到公司 = 人物和机构漏
```

产物：`scripts/kg_facts_report.py` 出「覆盖矩阵 + 缺口清单」，不靠手工统计。
缺口优先补词表、补源，而不是放宽阈值凑数。

### 七、评测：先金标，再优化

金标做法：

1. 用 `scripts/fetch_v3_history.py` 拉最近 30 天 raw artifact；
2. 抽 20 篇文章、100 个句子；
3. 人工标「每句应该抽出哪几条事实」，给出主体/动作/对象/数值；
4. 我初标，你抽查 20% 确认。

| 指标 | 定义 | 建议门槛 |
|---|---|---|
| A 档准确率 | A 档里事实正确的比例 | 0.90 |
| 主体正确率 | A 档里主体没抽错的比例 | 0.95 |
| 事件召回 | 金标里的关键事实被抽出的比例 | 0.60 |
| 事件类型覆盖 | 当月有事实产出的类数 | 15 类 |
| 噪声率 | 来自非新闻区的事实占比 | 0.05 |

门槛全部是建议值，跑完金标再定死；标定前不当承诺。

### 八、工作量（估算）

| 阶段 | 内容 | 估时 |
|---|---|---|
| P0 金标 | 100 条人工标注 + 评测脚本骨架 | 0.5 天 |
| P1 解析器 | 分句 + 依存 + schema 填槽 | 1.5 天 |
| P2 判档与存储 | A/B/C + 否定/传闻 + facts 落盘 | 0.5 天 |
| P3 覆盖报告 | 三层覆盖矩阵 + 缺口清单 | 0.5 天 |
| P4 接流水线 | Stage 2.5 改造 + GHA 提交 | 0.5 天 |
| 合计 | | 约 4 天 |

不含：词表持续扩充、月度调参。

### 九、风险与退路

| 风险 | 现象 | 对策 |
|---|---|---|
| 分词错 | 英伟达被切成英伟 + 达 | 解析前用词表最长匹配修边界 |
| 长句多动作 | 一句里 3 个动作抽不全 | 只取 root 主句，其余子句分开抽 |
| 否定 | 「没有提供」抽成「提供」 | 否定词表 + 降 B |
| 数字/单位 | 金额、份额、价格抽不到 | 正则 + 单位表 |
| 词表补不完 | 新公司一直冒出来 | 缺口报告驱动，只补高频 |
| 覆盖不达预期 | A 档很少、类目空一半 | 缩到 5 个强 schema |

退路：金标两轮迭代后 A 档准确率仍低于 0.80，就缩到 5 个强 schema（人事 / 发布 / 融资 / 收购 / 合作），其它不抽；再不行就承认零 LLM 只适合做「核验层」，不适合做「信息主体层」，再另议。

### 十、不做的事

- 不做开放式关系抽取（21 类之外一律不进 A 档）；
- 不替换 S4/S6 的 LLM 写作（事实层只提供事实和证据）；
- 不做跨语言、图片、视频内容；
- 不追求「每篇文章都出事实」。

### 十一、落地顺序

```
P0 金标（先定「准」）
   ▼
P1+P2 解析器与判档（拿金标验收）
   ▼
P3 覆盖报告（看缺口）
   ▼
P4 接 Stage 2.5（产物换 data/facts）
   ▼
回填最近 30 天历史（用现成 artifact）
   ▼
进 GHA 每日跑、按周看覆盖报告
```

回填 30 天这件事值得做：artifact 有现成 30 天，事实库一开始就有历史，覆盖报告立刻能看出缺口，不用等一个月。
