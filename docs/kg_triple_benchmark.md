## 10. 与历史结论的差异

| 项 | 历史 | 本报告 |
|---|---|---|
| 样本 | 3 / 10 / 18 / 40 篇混用 | 60 篇固定，dev 20 / test 40 |
| 端点匹配 | 包含匹配 | 默认精确，包含单列 |
| 关系映射 | 每脚本各一份 | 单一 `normalize_relation()` |
| 匹配算法 | 顺序贪心 | 最大二分匹配 |
| 缺失文档 | 静默跳过 | 记 0 分 |
| test 用途 | 与 dev 同批调参 | 只做最终验收 |

历史归档文档 `docs/archive/kg_ner_relation_eval_2026-11-19.md` 里的 「非 LLM 最高 test F1 0.11」是 18 篇 / 54 条、包含匹配、且未真正冻结 test 的结果。本报告在更严格的精确匹配和更大的金标上给出同量级但更低的数字，两者不能直接比较，结论方向一致：**非 LLM 方案离可入库（F1 0.7）差一个量级**。

## 11. 结论

1. 所有非 LLM 方案在严格口径下 F1 都低于 0.10，且排名差异大多在置信区间内，**没有证据支持「某个开源方案明显更好」**。
2. 主导误差是 `no_candidate`（80%–97%）：金标事实在候选池里根本不存在，过滤、打分、重排都无法把 F1 拉起来。
3. 端点错（`relation_only`）多于关系错（`endpoint_only`），说明瓶颈在**论元选择与跨句指代**，不在关系分类本身。
4. 并集不会带来质变：`union_all` 的召回略高，但预测数从 ~200 涨到 ~770，精度被摊薄，F1 基本持平。
5. 生产在跑的 `repo_rules` 产出量最大（560 条），但严格精度接近 0；这与历史「134 条里只认出 1 条」的现场结论一致。

### 选型建议

| 目标 | 建议 |
|---|---|
| 直接入事实层（要求 F1 0.7+） | 当前没有非 LLM 方案达标 |
| 做候选生成器，后续人工/规则过滤 | `hanlp_srl` 或 `gliner2_jointie`；两者在包含口径下最高（0.08 / 0.07），且互补 |
| 追求吞吐与可维护 | `ltp_srl`（1.2 秒/篇）优于 GLiNER2（3.6 秒/篇） |
| 不要做 | 继续加过滤规则；本报告里 80%–97% 的漏检是候选池没有，过滤只会更差 |
